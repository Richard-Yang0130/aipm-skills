# 产品决策链工作流说明

## 2. 工作流一：从想法到产品

### 适用场景

当你有一个产品方向，但还没确定它是否值得做、目标用户是谁、真实需求是什么、应该做成什么功能时，使用这条链路。

典型场景：

- “我想做一个 AI 工具，但不知道用户是不是真需要。”
- “这个方向值不值得做？”
- “帮我看看用户在吐槽什么。”
- “我想把这个想法整理成 PRD 给 Agent 开发。”
- “我需要一套能直接给 Claude Code / Cursor 执行的项目规范。”

### 推荐顺序

```text
product-insight-miner
  -> brd
  -> mrd
  -> vibe-prd-writer
  -> Claude Code / Cursor / Codex 开发
```

如果你已经有明确需求，可以跳过前面的调研和判断，直接进入 `vibe-prd-writer` 或 `ai-agent-prd-writer`。

### 2.1 product-insight-miner：产品灵感和用户痛点挖掘

**它解决什么问题**

很多产品想法的问题不是“不会写需求”，而是“还不知道用户到底有没有痛点”。`product-insight-miner` 用来从真实用户声音里挖机会，尤其适合想看小红书、X/Twitter、Reddit 上的吐槽、替代方案请求、竞品不满和付费意愿。

**典型触发语**

- “帮我挖掘用户痛点。”
- “去三个平台看看这个方向有没有机会。”
- “看看大家在吐槽什么。”
- “帮我调研一下 AI 写作工具的用户反馈。”

**输入**

- 一个产品方向或关键词。
- 目标用户群体，例如内容创作者、学生、AI 产品经理、独立开发者。
- 已知竞品，可选。
- 用户手动粘贴的帖子、评论、链接、截图文字，可选。

**执行过程**

1. 先明确挖掘主题、目标用户和已知竞品。
2. 进入三平台搜索采集：
   - Reddit 优先，重点看评论区、替代方案请求和强烈不满。
   - X/Twitter 关注早期用户、KOL、开发者和行业信号。
   - 小红书补充中文用户视角，看踩坑、吐槽、求推荐。
3. 每个平台会围绕痛点类、方案请求类、竞品吐槽类、付费意愿类关键词搜索。
4. 把素材结构化，记录来源、用户原话、痛点、情绪强度、可行动机会。
5. 做聚类分析，识别高频痛点、未满足需求、竞品盲区、潜在切入点。
6. 最后生成 HTML 可视化洞察报告。

**产出**

- 用户原声素材库。
- 痛点簇和机会点。
- 高价值用户反馈。
- 可作为 BRD/MRD 数据输入的洞察报告。

**注意事项**

- 它不负责直接判断商业可行性，商业判断交给 `brd`。
- 搜索覆盖有限，如果平台抓取效果不好，可以手动投喂素材。
- 最有价值的是分析层，不是“搜到多少条信息”。

### 2.2 brd：判断方向值不值得做

**它解决什么问题**

`brd` 回答的是“值不值得做”，不是“怎么做”。它适合在投入大量时间之前，对一个产品或业务方向做商业可行性判断。

**典型触发语**

- “这个方向值不值得做？”
- “帮我评估这个方向。”
- “这个能不能做？”
- “帮我写 BRD。”
- “我有个想法，帮我判断靠谱吗。”

**输入**

- 产品方向或商业想法。
- 用户已有数据，例如用户原声、访谈、市场反馈、竞品材料。
- `product-insight-miner` 的报告。
- 如果没有数据，Skill 会使用爬虫脚本补充公开数据。

**执行过程**

1. Phase 0：接收输入，确认数据源。
2. 如没有数据，会建议运行 `brd/scripts/fetch_market_data.py`，采集公开讨论和搜索结果。
3. Phase 1：消化数据，筛选方向。
4. Phase 2：做商业可行性评估，最少 2 轮，最多 5 轮。
5. 评估内容包括：
   - 商业机会是什么。
   - 为什么现在做。
   - 目标市场初判。
   - 用户声音和现有替代方案。
   - 我们的切入点。
   - 资源与约束。
   - 关键风险和待确认项。
6. Phase 3：生成前确认。
7. Phase 4：生成 `BRD.md`。
8. Phase 5：生成后自审。

**产出**

- `BRD.md`
- 数据索引附录。
- 决策建议，通常是：
  - 值得做。
  - 有条件地做。
  - 建议暂缓。
- 交接区，供 `mrd` 读取，避免重复提问。

**核心规则**

- 所有结论必须有数据索引。
- 不允许凭空编造市场规模、用户反馈、增长率。
- 没数据也可以继续，但必须明确标注“无数据支撑，仅供参考”。

### 2.3 mrd：从方向进入市场需求

**它解决什么问题**

BRD 判断“值不值得做”，MRD 判断“市场需要什么”。`mrd` 用于把用户原声和市场信号提炼成结构化的市场需求文档。

**典型触发语**

- “帮我写 MRD。”
- “帮我梳理市场需求。”
- “从这些用户反馈里提炼需求。”
- “这批数据能看出什么需求？”
- “帮我做市场需求分析。”

**输入**

- `BRD.md`，优先读取其中的交接区。
- 用户原声数据或 `market_data/raw_data.md`。
- `product-insight-miner` 的报告。
- 没有数据时，可复用 `brd` 的爬虫脚本。

**执行过程**

1. Phase 0：检测当前目录是否有 `BRD.md`。
2. 如果有 BRD，继承方向、用户、痛点和数据源。
3. 如果没有 BRD，但用户带了数据，则进入数据消化。
4. Phase 2：采集核心信息，使用自适应轮次提问。
5. Phase 3：生成前确认。
6. Phase 4：生成 `MRD.md`。
7. Phase 5：生成后自审。

**MRD 会具体写什么**

- 市场机会：解决什么问题、市场规模感知、关键市场信号。
- 目标用户：核心用户画像、需求优先级。
- 竞品格局：基本盘、趋势、差异化、现有替代方案、市场空白。
- 核心能力定义：我们要做什么、明确不做什么、差异化定位。
- 成功指标：怎么知道方向对了、阶段性里程碑。
- 风险与假设：关键假设、已知风险、待确认项。

**核心规则**

- P0/P1/P2 需求必须来自真实数据。
- 指标和优先级必须有索引。
- 没有数据支撑的指标不写，宁可短，也不虚构。

### 2.4 vibe-prd-writer：生成给 AI 编程 Agent 的项目规范

**它解决什么问题**

当你要把想法交给 Claude Code、Cursor 或 Codex 执行时，普通 PRD 往往不够。`vibe-prd-writer` 会生成 10 模块项目规范，重点是让编程 Agent 能直接理解边界、技术栈、数据模型、交互、状态和错误处理。

**典型触发语**

- “帮我写个 PRD。”
- “我想做一个 XX。”
- “帮我把这个想法变成可执行文档。”
- “我要 vibe code 一个产品。”
- “帮我写项目规范。”

**输入**

- 产品想法。
- 已存在的 `BRD.md`、`MRD.md`、`DESIGN.md`，可自动继承。
- 用户对技术栈、端类型、目标用户、功能边界的偏好。

**执行过程**

1. Phase 0：检测上游文档，判断从哪里开始。
2. 如果有 BRD/MRD，就读取交接区，继承已确认的信息。
3. Phase 1：需求澄清，主要用于没有上游文档的情况。
4. Phase 2：技术方案选型。
5. Phase 3：前端风格定调，优先复用已安装的前端设计 Skill。
6. Phase 4：生成 `PRD/` 文件夹。
7. Phase 5：质量自检，包括文件结构、模块内容、跨文件一致性。

**产出**

- `PRD/` 文件夹。
- 10 个模块独立文件。
- `README.md` 导航。
- 30 秒电梯介绍。
- Agent 加载建议。
- 上游数据追溯。
- 数据索引附录。
- 质量审查记录。

**适合谁看**

- AI 编程 Agent。
- 需要快速开工的开发者。
- 想把需求拆成工程任务的人。

**和 ai-agent-prd-writer 的区别**

- `vibe-prd-writer` 面向 AI 编程 Agent，强调可执行、无歧义、能直接开发。
- `ai-agent-prd-writer` 面向正式工作场景，强调需求文档质量、团队评审和业务语境。

### 2.5 ai-agent-prd-writer：正式 AI Agent PRD

**它解决什么问题**

用于写正式的 AI Agent 产品需求文档，更适合团队协作、业务评审和开发沟通。它不是只写功能清单，而是会先判断需求成熟度，再决定是引导梳理还是快速生成。

**典型触发语**

- “帮我写正式 PRD。”
- “写需求文档。”
- “梳理产品需求。”
- “帮我做产品设计。”
- “这个 Agent 功能帮我出一份 PRD。”

**模式**

- 引导模式：需求模糊时使用，一步步帮你把背景、用户、场景、痛点理清。
- 高效模式：你已经提供较完整材料时使用，快速确认关键点后生成。

**执行过程**

1. 判断模式。
2. 收集 PRD 地基信息：
   - 背景与语境。
   - 用户画像。
   - 产品现状。
   - 项目资料。
   - 技术栈和团队能力边界。
3. 确认输出配置：
   - 阅读对象：开发团队、AI 执行、业务方或管理层。
   - 产品类型：工具型、Agent 型、对话型、平台型等。
   - 需求规模。
4. 分模块生成 PRD。
5. 对 Agent/提示词产品做专项设计：
   - Agent 职责边界。
   - 工具调用。
   - 上下文管理。
   - 异常处理。
6. 做输出质量自检。
7. 本地文件管理和版本控制，边写边保存。

**产出**

- `{产品名称} PRD`
- 版本变更记录。
- 可给开发团队、业务方或 AI Agent 使用的正式需求文档。
